# ADR core-0022: Emby

Date: 26 November 2026
Status: accepted (Phase 12 stage 3; the lead put the owner's "properly, like it does with Jellyfin" in the brief)

## Context
Phase 12's "done when" is that a user of another server can do everything a Jellyfin user can, with no UI changes. Jellyfin was forked from Emby in 2018, and Emby still speaks the same HTTP API in most places: the same `/Items` queries and item shapes, `RunTimeTicks`, `ImageTags`, `PlaylistItemId`, `UserData`, `AuthenticateByName`, `/Audio/{id}/stream` and `/universal`, `/Sessions/Logout`. Copying the 900-line Jellyfin client would double every later fix. Where Emby differs was not taken from memory or old documents: every point below was seen on a real Emby 4.10.2.0 (`emby/embyserver`, pinned by digest) in GitHub Actions on 26 November 2026, first by hand with curl, then by the `emby` job's tests.

## Decision
1. **One client, two flavours.** `JellyfinClient` gains a `Flavor` (`Jellyfin`, the default, or `Emby`), set with `with_flavor`. The Emby-only code is in `encore-sources/src/jellyfin/emby.rs`; everything else is shared. `JellyfinSource` serves both: its `kind()` is `SourceKind::Emby` ("emby" in the database) and its capabilities are Emby's when the client is. `AnySource` needed no new arm.
2. **Telling them apart.** `/System/Info/Public` is asked at the address's root (both servers answer there). Jellyfin sends `ProductName: "Jellyfin Server"`; Emby 4.10 sends no `ProductName` at all, only `ServerName`, `Version` and `Id` (older Emby sent "Emby Server", also accepted). No product name with a server name, an ID and a version is Emby; any other product name is neither, and the Subsonic check runs as before. `ServerCheck.kind` gains `ServerKind::Emby`. Jellyfin and Subsonic are found exactly as before, with no extra request. The oldest Emby accepted is 4.8.0 (the version that reads `.lrc` lyrics as streams); CI runs 4.10.2.0.
3. **Paths and auth.** Every Emby call goes under `/emby` (Emby also answers at the root, but a reverse proxy may pass only `/emby`), unless the address already ends in `/emby`. The header is `X-Emby-Authorization: MediaBrowser Client=…, Device=…, DeviceId=…, Version=…, Token=…`, the same percent-encoded value as Jellyfin's (Emby decodes it: a device named "Sam's Pixel" shows as such). A player's URL carries `api_key` (Emby refuses Jellyfin 12's `ApiKey`; Jellyfin 12 refuses `api_key`).
4. **Signing in.** User name and password with `POST /Users/AuthenticateByName` (`Username`, `Pw`), as for Jellyfin; a wrong password is a 401 there too. **No Quick Connect** (`/QuickConnect/*` is a 404): `quick_connect_enabled` answers false without asking, the capability is off and `quick_connect_start` refuses with `QuickConnectDisabled`. Only the token is kept, in the keychain, as for Jellyfin.
5. **Who a token belongs to.** Emby has no `/Users/Me` (a 500, "Unrecognized Guid format"). A device knows its user ID from the sign-in and asks `/Users/{id}` (for the avatar). The companion has only the token, and Emby does not check that a user ID in a path belongs to the token (a user can read another's record), so the ID can't come from the device. Instead: every authenticated request makes or updates the session of the calling device (client name plus device ID) under the token's own user, so the companion calls `GET /Sessions` with the token and takes the user of its own session (`Encore companion`, `encore-server`). An administrator's token lists everyone's sessions, but only one is the companion's. Checks for Emby run one at a time in the companion, so two can't share that session; two users there is refused, not guessed. The user record's `ServerId` must match the claimed server, as for Jellyfin.
6. **The library mirror.** The same paged `/Items` queries and the same delta (`minDateLastSaved`, the server's `Date` header as the cursor). Emby sends no `HasLyrics`, so songs are asked for with `MediaStreams` and a song has lyrics when it has a text subtitle stream.
7. **Lyrics.** Emby keeps a song's sidecar `.lrc` as a `Subtitle` stream with codec `lrc` on the song (seen in CI; lyrics inside the tags are said to come the same way, not tested). Any text subtitle stream is read, an `lrc` one first. `/Audio/{id}/Lyrics` must never be called: Emby reads "Lyrics" as a container name and fails with an ffmpeg error. The adapter reads the item's streams and media source, fetches `/Items/{id}/{mediaSourceId}/Subtitles/{index}/Stream.js` (lines with start ticks; it starts with a byte order mark), and turns it into LRC (plain lines when no line has a time), which the one lyrics parser reads. `Stream.lrc` came back empty, so it is not used.
8. **Playlists.** `POST /Playlists` takes its name, songs and user as query parameters (a JSON body is a 500). Adding is at the end only. Rename has no call of its own (`POST /Playlists/{id}` is a 404): the item is read from `/Users/{user}/Items/{id}`, its `Name` changed and saved back with `POST /Items/{id}`. Delete is `DELETE /Items/{id}`. **Entry IDs can't be trusted to name an entry**: after some moves (moving the last song, in CI) Emby gives the entries new IDs by position a moment later, not after every move, and its listing may go on pairing songs with the old IDs meanwhile; after a removal it closes the gap in the IDs a second or so later. A removal by the listed ID took the wrong song in CI with either reading of the IDs, while the order of the songs in the listing was always right. So the mirror names an entry by position and song (as for Subsonic, `"<position>:<song id>"`), and a removal, a move or an insert is done on the songs: read the playlist, find each entry as the Subsonic adapter does (the same song nearest its old position), work out the new order of songs, add that whole order at the end, then remove every entry that was there before by the set of their IDs, which is the same set whichever way Emby pairs them. Before that it waits up to 15 seconds for a gap from an earlier removal to close, so no ID shifts under it. An append at the end is a plain add. Emby's own `Move` call is not used.
9. **Favourites** are `POST` and `DELETE /Users/{user}/FavoriteItems/{id}` (Jellyfin 12's `/UserFavoriteItems` is a 404). The whole set comes back each sync with `filters=IsFavorite`, as for Jellyfin.
10. **Play counts.** Read with `filters=IsPlayed` as for Jellyfin. Emby's lists say `PlayCount: 0` beside `Played: true` (the item itself has the real count) and leave out `LastPlayedDate`, so a played song counts at least once and has no last-played time. Emby does take playback reports (`/Sessions/Playing`, `/Sessions/Playing/Stopped` raised a play count in CI), but Encore sends none to any server: `playback_reporting` stays off, the companion keeps the history.
11. **Streams, covers, downloads.** `/Audio/{id}/stream?static=true` (with HTTP ranges) for the original, `/Audio/{id}/universal` for a capped transcode, `/Items/{id}/Images/Primary` (with `format=Png` for the palette) for covers, all as for Jellyfin. Emby serves images without a token.
12. **The companion** checks an Emby token the way it checks a Jellyfin one: on a trusted address from `ENCORE_MEDIA_URLS`, whose `/System/Info/Public` must carry the claimed server ID and says it is Emby; then point 5. Nothing of the token is kept.
13. **Testing.** Hand-made fixtures (`tools/fixtures/emby/`, invented, shapes as Emby sent them) for the adapter's and the core's unit tests and the companion's; in CI, the `emby` job starts a real Emby on the same generated tone files as the Navidrome job, finishes Emby's first-run wizard through its API with a throwaway administrator, adds a user who is not one, and runs `emby_flow_over_http` (encore-core) as that user and `emby_check_over_http` (server) for both users.

## Consequences
- Emby support is a few hundred lines beside the Jellyfin client, and a Jellyfin fix reaches Emby where the wire format is the same. A Jellyfin client is unchanged unless its flavour is set (tested).
- A removal, move or insert on Emby rewrites the playlist's entries (one listing, one add and one removal per 200 songs), so Emby's entry IDs change on every such edit (Encore keeps none of them), and it may wait a few seconds after a removal. If the add went through and the removal didn't (the network dropped between them), the playlist holds its songs twice until the user fixes it; nothing is lost.
- In the CI container Emby 4.10 picked up neither `cover.jpg`, `folder.jpg` nor a cover in the tags within minutes (its albums are made from tags and have no folder), so CI sets the cover through Emby's own image upload, as its web app does. Whether a real library's local covers show is Emby's own scan; the adapter reads whatever `ImageTags` say.
- An Emby behind a reverse proxy that passes only `/emby` is not found from its bare address (the public check is asked at the root); typing the address with `/emby` works.
- Emby's lyrics from an online lyrics plugin come the same way (as streams) and are read the same; not tested.
- Each companion check for Emby leaves the companion's own session ("Encore companion") listed in Emby's devices and sessions, under the user it last checked.
