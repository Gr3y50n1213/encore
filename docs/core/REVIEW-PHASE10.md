# Phase 10 review: core and server track

24 November 2026. Phase 10's "done when" line is *v2 beats v1's early-skip rate in an offline replay test* (`docs/ROADMAP.md`). The core and server track's part covers:
- sound analysis: YAMNet in plain Rust, a small hand-built profile, a ranged reader for the original file, the store table and the core calls;
- sound-aware smart picks: similarity, candidates, flow between songs and a taste in sound;
- the learned ranker, trained on the device or on the companion server;
- sharing the analysis between devices through the companion server;
- moods and mood mixes;
- the offline replay that compares version 1 with version 2.

The plans are ADR core-0019 (the sound fingerprint) and ADR core-0020 (sound in the engine and the learned ranker). The API is CORE-API v8.

Also on the branch, and not in the plan: playlist fixes found by the owner's own use on 23 and 24 November (`delete_playlist`, a 403 fork, local IDs kept through a pull, a name the server can keep). They are under "Found and fixed".

## Deviations from the plan

1. **Devices analyse the audio, not the server.** PLAN-PRODUCT (lines 82, 214, 297 and 305) and the roadmap row say the companion server reads the audio. ADR core-0019 moved it to the devices for three reasons: the server keeps no media-server token (core-0009), most people have no companion server, and the owner's Jellyfin runs on a weak PC that must not be made to transcode. The server only stores the rows and hands out short claims, so two devices never work on the same song. The shared plan text was not changed (see Follow-ups).
2. **The ranker runs in Rust, not ONNX or Core ML.** PLAN-PRODUCT line 278 says the model is exported to ONNX or Core ML. Ranking takes microseconds, and a runtime library would add a native file per ABI and an Android page-size question. The roadmap's "on-device Core ML and ONNX models, NPU paths" and its Core ML, NNAPI, QNN and DirectML columns are not built and not needed. YAMNet runs the same way, on the CPU, in plain Rust.
3. **Training is "when due", not nightly** (PLAN-PRODUCT line 278). One rule (`learn::due`) serves the device and the server: 300 plays to start, then 200 new plays or a week with new plays; a new epoch or a cleared history starts over. A server with no devices asking does no work.
4. **Moods are rules, not a clustered mood map.** Eight fixed moods from energy, brightness and dynamics (thirds of this library) and tempo, each with at least 25 songs once 60 are analysed. There is no valence, acousticness or danceability and no model-written titles: ADR core-0019 does not claim what signal processing cannot measure. The cold start gives up to two mood mixes where PLAN-PRODUCT 7.1 says up to three.
5. **Similarity uses the YAMNet embedding alone.** Adding the hand-built texture or tempo to it lowered precision (38.5% and 36.0%), so the profile is used only for flow between songs and for the cold start.
6. **Opus songs are unreadable.** Symphonia has no Opus decoder. They are marked, never guessed, and can be retried.
7. **The build order changed.** Phase 12 comes before Phase 11 (owner, 23 November). This is the owner's change, not the track's.

## Found and fixed during this phase

1. **CI clippy findings (runs 43444224422, 43465938078 and 45272621233).** Run 43444224422 (41c90ba) refused `chunks_exact` with a constant size in `encore-analysis`; fixed in 899145f with `as_chunks`. Runs 43465938078 (8631a7e) and 45272621233 (e39a007) refused `recs-replay` for too many arguments (8 of 7); fixed in c77420b.
2. **A tool stopped compiling (run 43448503593).** `fixture-recorder` built a `Response` without the new `content_range_total` field. Fixed in 8631a7e.
3. **The ranker beat the hand-tuned score on held-back plays but made worse picks.** It was judged across all songs while picks come from the top of the range. The gate now judges on the plays the person likes most, and the trees may only split on the signals the hand-tuned score cannot see (ADR core-0020, "What the experiments taught").
4. **A sound-based guess for never-played songs at full strength cost the clean-tag listener two points.** It leans a quarter, and never above what a song finished once or twice earns.
5. **The first replay was too coarse.** 1,200 picks a listener could not separate versions; it is now 4,800.
6. **A playlist made on the owner's phone vanished at the next pull (e4fefda).** Its creation was held up in the outbox, so it still had a local ID. A quick pull lists every mirrored ID the server no longer has as removed, and the local ID was one of them, so the playlist was deleted with its songs. Local IDs are no longer offered as mirrored IDs and removal skips them: `a_quick_pull_never_removes_a_playlist_the_server_hasnt_made_yet`.
7. **A playlist the server refused changes to blocked every write behind it (e62c291, 24 November).** The owner's server lost the owner of a playlist made on the phone, then answered every later change with 403. Encore read 403 as an ended sign-in and kept the write waiting; writes go in order, so songs added on the phone never reached the server. A 403 is now "not yours to change". The refused playlist is forked: it gets a new local ID and is made again on the server with its name and songs, as the user's own; its other waiting writes are dropped and the rest of the queue goes on. A pull keeps the name of a playlist whose rename is still waiting. `a_playlist_the_server_wont_let_us_change_becomes_our_own`.
8. **A new playlist's name could not be kept by the server (6d1712a, 23 November).** On the owner's Windows Jellyfin server a playlist named "Favorites " (trailing space) was saved in a folder Windows renamed, and Jellyfin's next scan removed it. A new playlist is made with the name it has when it is sent (a rename that came first no longer leaves the first name behind), without spaces or dots at its ends: `a_new_playlist_reaches_the_server_with_a_name_it_can_keep`.
9. **There was no way to delete a playlist (8ecbef5, 24 November).** `delete_playlist` removes it here at once and queues the server's delete; its waiting writes are dropped; one the server never saw is only forgotten. No Undo, the app asks first. Jellyfin answers a delete the user may not make with 401, like an ended sign-in; when the sign-in still works the write is now refused instead of retried for ever. `a_deleted_playlist_goes_here_and_on_the_server_and_its_waiting_writes_go_too`. The 401 case has no named test.

## Not claimed

- **Real music beyond MP3:** FLAC, AAC, ALAC and Vorbis decoding is untested.
- **A real library:** nobody has run the analysis on the owner's library, so "sounds like" and the moods have not been judged by ear. Every number in the ADRs is a starting value.
- **Phone speed:** 2.4 s of work a song is a figure from a weak desktop CPU. The core's estimate before it has measured anything is about 1.2 MB and 3 s a song.
- **The ranker on real plays:** it has not been trained on a real history.
- **A real analysed row through the server:** see the gap above.
- **The 401 on `delete_playlist`:** no test.
- **Other platforms:** Apple and Windows and Linux have the API in their bindings; their screens and job scheduling are their own tracks and are not built. The Dart bridge lacks `delete_playlist`.

## Follow-ups

- **"Delete sound analysis" leaves the shared rows on the companion server.** Nothing in `server/src` deletes from `sounds` (only expired claims are deleted), and removing a profile everywhere doesn't touch it, because the rows belong to the media server and not to a profile. After a Delete, the next run takes the rows back from the server. The Android dialog says Encore "forgets what every song sounds like" and that "turning it on again starts over". With a companion server that is not true. Needs an owner decision: delete the server's rows too, or say so in the dialog.
- **The screens say "about 130 numbers per song are kept". The database keeps about 1,600.** 130 is what the engine holds in memory (a 128-number projection and five values). The profile database keeps the 1,024-number embedding and 521 class scores (1,546 bytes) and a 58-byte profile, and the companion server keeps the same rows. The text is in `SoundUi.kt` (two places) and in mock-up 44 (two places). The privacy line added in this commit (`docs/shared/PLAN-PRODUCT.md`, section 12) uses the true number.
- **Add `delete_playlist` to the Dart bridge** when the Windows and Linux track needs it.
- **The shared plan still says the server reads the audio** (PLAN-PRODUCT lines 82, 214, 297 and 305, and the Phase 10 row of the roadmap). It needs the owner's word to change.
- **Remove the `push` trigger from `.github/workflows/sound-spike.yml` when Phase 10 merges.** The file says so.
- **Add a real-embedding row to the two-device test**, so the server's sharing is proved on an analysed song and not only an unreadable one.
- **Judge on the owner's library:** run the analysis on the owner's phone, then read How suggestions are doing.
